Plan for bringing the **Instrument Simulator** back into SimpleFighter. It was once an in-builder feature called "instrument" (play drums and piano on the keyboard for fun); the dev removed it several versions ago and rebuilt it as a separate app. Agreed to eventually port it back, captured 2026-09-04. NOT YET STARTED — this is the design/scope record so the port is a straight translation when we start.

The standalone app lives OUTSIDE this repo at `C:/Users/tonys/OneDrive/Desktop/InstrumentSimulator-src/InstrumentSimulator-1.00rv` (the dev's own app). We already modernized it there, so what gets ported is clean: a `class instrument` in `includes/inst.nvgt` (a note-key table drives note indices 1-36 in QWERTY order), plus a `recorder` class in `includes/recorder.nvgt`. Follow all SF stability rules when porting ([[project_stability_rules]]): CRLF, double coords where relevant, builder audio form, alphabetical menu slot ([[feedback_alphabetize_builder_entities]]), and confirm section-by-section per [[feedback_confirm_before_implementing]].

## The deliberate scope decision (the important part)

**The SF port lets you RECORD and PLAY BACK a performance, but NOT save or load recordings. This is on purpose.** In the standalone the recorder can `save()` a performance to an encrypted `.rec` file and `load()` it back through a file menu; those two paths (and their Alt+S / Alt+L hotkeys, plus `input_box`, the recordings directory, and the encryption key) are dropped from the SF port. Keep only: Alt+R to record with the countdown, Alt+Return to stop, Alt+P to play back the current session's recording. So a recording is an in-session toy — play, capture, hear it back — with no persistent files inside SimpleFighter.

**Why:** the dev wants the instrument to stay a lightweight fun feature inside the game, not a mini-DAW that writes files into SF's data. Recording is for immediate playback in the moment, not for building a library.
**How to apply:** port the `recorder` class WITHOUT `save()` / `load()` and without wiring Alt+S / Alt+L; leave `record_note` / `record_stop` / `record_bend` / `play()` / the transport (record, stop, play) intact.

## What the port must adapt to SF's conventions

- **Audio** — the standalone bundles its own `sound_pool.nvgt` (with `update_sound_start_values(slot, pan, volume, pitch)` and `play_stationary` returning a slot int) and needs `rotation.nvgt` for that pool. SF uses its own audio stack (NVGT sound_pool + `get_pack_sound`/`get_map_sound` glob lookups per [[project_audio_model]]), so drop the bundled pool and `rotation.nvgt`; re-express note playback and the live pitch bend through SF's pools. pan/volume are unused in the app (always 0) — only pitch varies — so the SF version only needs live pitch control. The standalone's `instpool` (note playback) becomes a global SF pool like every other entity's (compare `bikepool`), and the recorder's own playback pool likewise.
- **Effect spaces** — register the instrument's note pool in `apply_effect_pools()` (`src/includes/builder/audio/effect_space.nvgt`), which runs each frame and walks every entity pool through `apply_all_effects(x, y, pool, z)` so effect-space reverb/echo/filters color that pool's sound. Add a line like `apply_all_effects(me.x, me.y, instrumentpool, me.z)` — use the PLAYER'S position, since the notes play stationary at the player (the player is the one operating and hearing it), the same way `p`/`hookpool`/`sonarpool` are registered against `me`. Do the same for the recorder's playback pool. Miss this and the instrument's notes stay dry inside a reverb zone while everything else is wet.
- **Sound assets** — clips are `pianos/<name>/p<N>.ogg` and `drums/<name>/d<N>.wav` (pianos are .ogg, drums are .wav), with instruments discovered by folder listing. Decide where these live under `sf/sounds/` ([[project_sound_assets_layout]]) and use SF's folder-listing helper so both decompiled folders and compiled packs work.
- **Input** — the app owns the keyboard in a raw `while(true)` loop reading `KEY_*` and exits with `exit()`. In SF it must be a self-contained modal loop (like the builder's other modal screens) that captures keys while open and returns to the game on Escape (NOT `exit()` the whole game), and gate it so only the active instrument runs `update()` if more than one is ever placed. Mind the key_pressed one-shot rule [[project_nvgt_key_pressed_oneshot]].
- **Menus** — replace the bundled `custom_menu` with SF's menu/form system.
- **Category (settled 2026-09-04): interaction, NOT audio.** The audio category is passive emitters (sources, ambiences, speakers, effect spaces, url streams) the player never operates; the interaction category is things the player actively uses (sign, clock, calendar, item, sensor, switch, text square). The instrument does nothing until the player plays it and responds continuously to keypresses, so it belongs with interaction — category is about how the player relates to the entity, not that it outputs sound (everything in SF does). File goes at `src/includes/builder/interaction/instrument.nvgt`; the build-menu entry named "instrument" lands in the interaction tab in its alphabetical slot ([[feedback_alphabetize_builder_entities]]), between clock and item (calendar, clock, instrument, item, sensor, sign, switch, text square). Add a help topic ([[feedback_tp_prose]]).
- **Spier, entity menu, and obscurity zones** — add the instrument to `spy_check_entities()` (`src/includes/main/globals/spier.nvgt`) so the inspection cursor announces one when the spy cursor lands on it, and to the on-map entity list menu, each gated by `is_obscured("instrument", "spier")` / `is_obscured("instrument", "menu")` (`src/includes/builder/zones/obscurity_zone.nvgt`) so an obscurity zone can hide it exactly like any other entity. Also add "instrument" to the obscurity zone builder's list of obscurable entity types so authors can pick it.
- **Single and ranged forms** — the instrument must build as either a single tile or a ranged rectangular area, using SF's standard build-mode single/ranged pattern (compare sign and door; [[project_map_format]] single/ranged one-keyword rule, with the map parser distinguishing the two by token count and the builder form's build-mode list offering "single" and "ranged"). A single instrument is one tile you play from; a ranged one covers an area the player can play from anywhere inside.
- **Map error checking** — the instrument's map line must be covered by the map errors tool ([[project_map_error_template]] Tier 1 + [[project_map_error_tier2_plan]] Tier 2). Give its `read_*` the correct `sd.length()` count gates in the parser dispatch so a wrong-value-count line is flagged rather than silently dropped (Tier 1), and add an `instrument_semantic_error()` (modeled on `door_semantic_error`/`passage_semantic_error`) that validates the coordinates, the numeric fields, and that any named instrument/sound folder exists, returning an error string plus an `int &out col`. Because it has single and ranged forms, the count checks and the semantic field offsets must cover BOTH token counts and the 2d vs 3d z-field variants ([[project_stability_rules]] — the mapmode-locked, multi-valued `sd.length()` rule).

## Class shape to translate (already built in the standalone)

`class instrument` holds: `instcad` (1 piano / 2 drums), `overlap`, `staccato`, `pitchable`, `pitchtime`, `pianoslot`/`drumslot`, `pitch`, `piano`/`drum` (current instrument folder names), `pitchtimer`. Methods: `update()` (per-frame input), `play_note(idx)`, `stop_note()`, `cycle_category()`, `cycle_instrument(dir)`, `toggle_overlap()`, `toggle_staccato()`, `bend_pitch(dir)`, `reset_pitch()`. The array/spawn/destroy trio (`instrument@[] instruments`, `spawn_instrument`, `destroy_all_instruments`) already matches SF's entity pattern (compare `bike`). Recorder event model: `delay:P:cad:pitch:path` (note-on), `delay:S:cad` (note-off), `delay:B:pitch` (bend); playback tracks a per-category slot so articulation and bends reproduce.
