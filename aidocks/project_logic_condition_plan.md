Notable build-time refinements from the plan: the build form uses an on-form "add elseif branch" button opening a two-field sub-form (not a post-form Add/Finish menu), buttons ordered add-elseif / okay / cancel; the Tier 2 condition-syntax check NEUTRALIZES `%tokens%` to a number before splitting on spaces (so an item name with spaces validates); and the Tier 1 mirror + despawn wiring landed in §2, not §4. A collaborative design (post-14.8) for a new builder element that brings conditional branching to maps. Grew out of studying an external reference game's ID-based interactable system and adapting it to SF's intentionally ID-less model — the key realization: SF already has the triggers (switch/sensor/input/map_timer) and the actions (slash commands), so it only lacks a *condition* layer and a *memory* layer, and both can be global/name-based, sidestepping the no-IDs constraint. See [[project_universal_state_tokens]] (conditions read these) and [[project_feature_ideas]].

**Why an element, not a `/if` command:** an element is self-contained (holds its own branches, runs its own commands) so it never has to name/reference another entity — dodging no-IDs entirely; it matches SF's form-based authoring; and structured if/elseif/else fields beat a stringly-typed `|`/`&` action string.

**SETTLED so far:**
- Element name: **logic condition**.
- **Mode field: contact / interact / watch** (mirrors sensors' contact-vs-interact, adds watch). One shared coordinate area for all three; the if/elseif/else evaluation is identical across modes — mode only decides WHEN it's asked.
  - contact: evaluates on entering the area (sensor-like).
  - interact: evaluates on the interact key while inside (switch-like).
  - watch: evaluates continuously while the player is inside the area — **AREA-SCOPED** (chosen over global; cover the whole map for a global rule). Fires the winning branch only when the winning branch CHANGES (transition tracking), not every frame, or it would spam. else fires once when the winner flips to it. This mirrors the conditional-gate pattern from an external reference game.
- **Area:** single tile or ranged, plus z on 3d — like other elements.
- **Condition syntax:** built from the universal state tokens (%health%, %points%, %x%, etc., which expand to live values before evaluation — SF's `[element.property]` analog for GLOBAL state), with operators `< > <= >= == !=` and logical joiners `and`/`or`/`&&`/`||`.
- **Branches:** an if (condition + command), any number of elseif (condition + command) pairs, and an else (command). Branch commands are handed to comstack (trusted source, like other elements — see [[project_trusted_commands_compiled]]).
- **On-disk layout (SETTLED):** `logic_condition <coords> <mode> "<if cond>" "<if cmd>" [ "<elseif cond>" "<elseif cmd>" ]... "<else cmd>"`. First two quoted fields = if (cond, cmd); LAST quoted field = else command, which is **mandatory but may be empty (`""`)** when there's no else; everything between = elseif pairs (even count). Deterministic parse (no parity guessing): peel first two = if, last = else, middle = elseif pairs. Field count after mode is always odd and >= 3 — a cheap Tier 2 structural check. Chosen over an infer-else-by-parity rule because it's unambiguous for hand-authors. Quoted command fields follow the shared escape convention (see [[project_command_field_no_nested_quotes]]).
- **What conditions read (SETTLED — option B):** the universal state tokens PLUS the player's map inventory (item counts). Ships standalone (both already exist in-game); does NOT wait on flags. **UPDATE (14.9): the named-flag store is now BUILT ([[project_flag_store_plan]]) and exposes `%flag:name%` as a universal token — so when logic conditions are built, conditions read flags for free (e.g. `%flag:door_opened% == 1`) with NO change to this element's design.** Inventory-reading syntax still open (see below).
- **Precedence (SETTLED):** match StoryBuilder's naive **left-to-right** fold — no parentheses, no and-over-or binding, no `not`/`!`. Simple, predictable-if-documented, consistent with the dev's own app; grouping needs are met by elseif chains + (eventually) the flag store. Numeric compares must accept **floats** (stn), unlike StoryBuilder's integer-only test.

**OPEN / undecided:**
- The **condition evaluator** — a small expression parser (tokens already substituted to values → tokenize comparison/logical operators → left-to-right fold). The main new code; self-contained and testable. Adapt StoryBuilder's clause-folder + quote-aware tokenizer + the `""`-sentinel trick.
- **Build form for elseifs (SETTLED — REFINED 2026-09 to an on-form button):** one form collects coords, build-mode, trigger-mode, the if condition + command, the else command, and single-use. It has three buttons in order: "add elseif branch" (opens a small sub-form with both fields — elseif condition + elseif command — plus okay/cancel; its okay appends the pair and returns to the still-open main form, its cancel discards the branch), okay (builds immediately with whatever branches exist), then cancel. This replaced the earlier post-form "Add / Finish" manage-loop menu so a plain if/else needs no extra Finish step (dev's call). Chosen over a single delimited box (option A — rejected: conditions are operator-rich, `= > <` and spaces collide with any delimiter) and over fixed elseif slots (option C — fallback, but caps count). Manage-loop gives arbitrary N, clean per-field entry, screen-reader-friendly sequential prompts.
- **Firing / re-arm (SETTLED):** defaults are repeatable/continuous — contact fires on entering the area and re-arms on exit (sensor-like); interact fires on each interact press while inside; watch fires each time the winning branch changes (transition tracking). Plus a shared **single-use bool** (like sensors' single-use): when set, fires once then goes dormant (contact/interact never fire again; watch stops after its first satisfied branch). Pairs naturally with flags later, but useful standalone (e.g. single-use contact that grants points once).
- **Builder-menu category (SETTLED):** the **interaction** category, alphabetically among its siblings (switch/sensor/inputs) — it's a placed, command-firing trigger like them. (Not misc, despite watch mode's map-timer flavor, because it's placed and trigger-like.)
- **Inventory-reading syntax (SETTLED — option 2, `%item:name%` count token):** item count is just a value — `%item:keycard% >= 3`, presence = `%item:keycard% > 0`. Uniform with the comparison model (evaluator needs NO inventory-specific clause), handles counts, and reuses the token layer. Resolved like `random(...)`: scan for `%item:<name>%` (name may contain spaces, read to the closing `%`), replace with the map-inventory count before evaluation. Doubles as a UNIVERSAL token usable anywhere (e.g. `speak you have %item:coin% coins`), so it's really a small token-system addition that logic_condition depends on. Reads the map inventory (give/take/getall fill it), not the account-wide inventory.
- **Map-error tiers (SETTLED):** Tier 1 sets `lenok=true` (command-carrying element, like switch/sensor/inputs). Tier 2 (`logic_condition_semantic_error`) validates: coords in bounds, mode in {contact,interact,watch}, field count after mode odd and >= 3, single-use bool valid, AND — chosen — **the condition expressions themselves** (option 1): each condition (if + every elseif) must parse as valid `value op value` clauses joined by and/or/&&/||, operators from `== != > < >= <=`, and every `%token%` used must be a recognized name. Can't check runtime values (tokens unexpanded at check time) but fully checks structure + spelling, so typos like `%helth%` surface in the map-errors box. Validator reuses the evaluator's tokenizer.
- **Single/ranged detection (SETTLED by convention):** single tile or ranged area, detected by the same quote-scan approach the inputs/switch use (count leading numeric coord fields before the first quoted field), so it works despite the quoted command fields.

**RUNTIME DECISIONS (settled 2026-09, all as recommended):**
1. **Read scope at launch: include `%item:name%` now.** Build the inventory-count token as part of §1 alongside the evaluator, so conditions can test item counts (`%item:keycard% >= 3`) from day one. Reads the MAP inventory (the `inv` store that give/take/getall fill and that is cleared on map load), 0 if the item isn't held. Universal token (usable in any command/text like `%flag:name%`).
2. **Malformed condition at runtime → false, fall through.** An unparseable condition evaluates to false so evaluation continues to the next elseif / the else; one bad branch never dead-ends the element (the mandatory else is the safe landing). (Tier 2 should catch these at author time; this is the runtime backstop.)
3. **`watch` re-arm: reset on exit, re-fire on re-entry.** Leaving the area clears the remembered winning branch, so re-entering re-evaluates and fires the current winner fresh (mirrors contact's re-arm-on-exit). While inside, still fires only when the winning branch CHANGES.
4. **single-use: consumed only on a real if/elseif match.** The element stays armed until an actual if or elseif branch wins; an else win (nothing matched) does NOT burn the single-use. So a single-use element waits for its real condition to become true rather than using itself up on the first miss.
5. **Empty if/elseif commands allowed.** An if or elseif command may be `""` — a deliberate do-nothing branch (match this and intentionally do nothing, without falling through to else). Symmetric with the else, which can already be empty. An empty winning command is a silent no-op.
6. **`%item:name%` reads to the closing `%`.** Item names may contain spaces/underscores (they are inventory identifiers give/take use), so the token name is everything from after `item:` up to the closing `%` — e.g. `%item:health kit%`, `%item:gold_bar%`. (Unlike flag/variable names, which are letter-led no-spaces.)

**REFERENCE — StoryBuilder app** (`C:\Users\tonys\OneDrive\Desktop\StoryBuilder-1.20`, NVGT, the dev's own): its `evaluate_condition()` (`includes/story_interpreter.nvgt:58-170`) is a self-contained left-to-right CLAUSE FOLDER — shift `var op value`, eval to bool, fold via an and/or flag, check next connector. Operators `== != > < >= <=`, connectors `and/or/&&/||` (case-insensitive). Reusable: that fold shape, its quote-aware tokenizer `parse_story_tokens` (`story_functs.nvgt:58`), and its trick of rewriting `""`→a sentinel before tokenizing so empty quoted strings survive. KEY INSIGHT: StoryBuilder's if/elseif/else machinery (forward line-scan + if_result_stack) is NOT needed for SF — SF's element holds branches as fields, so it needs only the evaluator, not control-flow scanning. And SF's evaluator is even simpler because the universal state tokens expand to values BEFORE evaluation (`%health%`→`140`), so it compares literals with no variable lookup. MUST-FIX vs StoryBuilder: it's integer-only (is_digits), SF must accept floats (coords/health are doubles; use stn). StoryBuilder has no precedence (and/or fold strictly left-to-right, `A or B and C` = `((A||B)&&C)`), no parentheses, no `not`/`!`.
