## Slant — a directional ramp/incline builder entity (DESIGN SETTLED 2026-08, not yet built)

A new **construction** builder entity. Modeled on the "slant" in an external reference game (its map-syntax glossary), adapted to SimpleFighter's conventions. Design was walked through and settled with the dev; the pieces below are agreed.

**Build status (2026-08):** COMPLETE & dev-confirmed fully functional — walking, footsteps, re-attach, jump/land, and camera all working, plus §6 docs done (`sf/docks/builder/slant.txt` help topic + 14.3 changelog entry "You can now build slants..."). Whole feature shipped; drop from this backlog once 14.3 is released (it becomes changelog/todo history). DONE — §1 data+lifecycle, §2 read/write, §3 build form, §4a floor-tile spawning (diagonal ramp + top landing), §4b `slantcheck` walk-across elevation mechanic, §5 wiring, camera follow (`slant_camera`) (all in `src/includes/builder/construction/slant.nvgt`). Note (fixed 2026-08): footsteps on a ramp are handled by `slant_snap_player()` called at the **top of `playstep()`** (`map.nvgt`) — it runs the full attach/snap (`slantcheck`, which *detects* attachment and snaps on the same frame, so even the first step onto the ramp is covered) *before* `playstep` reads the tile underfoot, so the step sounds the ramp's own tile, not whatever floor sits at the pre-snap height *underneath* it (that floor otherwise played, either instead of or — with an earlier slantcheck-plays-it attempt — *alongside* the ramp tile as a double). Do NOT also emit a step sound from `slantcheck`. Also (fixed 2026-08): the "on-ramp" detection attaches when the player is within the footprint at a height in the ramp's body (`base_height..surface`), not only when exactly on the surface tile — so you re-attach walking back onto the hill from the high side after falling off (a ramp with no top landing). Above the surface = fall/jump landing (elsewhere); below the base = walk under an elevated ramp freely. Also (fixed 2026-08): the **camera** rides slants too — `slant_camera()` (in `slant.nvgt`), the camera analog of `slant_snap_player`, is called at the top of `playcam()` (`map.nvgt`, the G+T playback + every incremental camera move) and at the top of the `camera_describe` read (`game_handlers.nvgt`, the G+R speak). While the camera's horizontal position is over a slant footprint it snaps the camera's vertical axis (`cam.y` 2d / `cam.z` 3d) to the ramp surface, so G+R/G+T report and play the ramp's own surface tile and its climbing height. Why it was broken: a **staircase** in 2d is one solid filled block (`spawn_platform(minx,maxx,miny,maxy,…)`), so the camera finds its tile at any height in the span; a **slant** is a diagonal run of one tile per column, so the flat camera plane swept straight past the diagonal tiles. Snap is **unconditional** over the footprint (dev chose "ride the ramp like the player" over keeping vertical camera freedom). PENDING — §5 wiring (construction menu entry between platform & staircase, parser dispatch, **`slantcheck()` call placed immediately before `fallcheck()`** in game.nvgt, `destroy_all_slants()` in clearmap), §6 docs (`slant.txt` help topic + changelog under the open 14.3). §7 slant-aware jump landing is **CANCELLED** — the dev confirmed (2026-08) jumping and landing on slants already works perfectly; no special logic needed (the non-backing floor tiles are seen by the existing `user_platform_at` landing).

**What it is.** A region you walk across that changes your **elevation** as you move — it raises (or lowers) you by a set **step height** for every tile you move along it. Think of it as a staircase you climb by walking *sideways* instead of pressing up: you set how tall each step is, and moving across it carries you up or down automatically. It sits on SF's whole-level grid — each tile you move lands you on a whole level.

**You move yourself horizontally; the slant moves you vertically.** The horizontal direction you walk never changes on its own — your stepping does that. The slant only changes elevation: **y** on 2d maps, **z** on 3d maps.

**Modes.**
- **2d** — elevation is `y`. Walking left/right (x) changes `y`.
- **3d** — elevation is `z`. Walking left/right (x) or forward/backward (y, the flat ground) changes `z`.
- **topdown** — NOT offered. No elevation axis, so a slant has nothing to change (same reason jumping/hooking are disabled on topdown). The builder simply won't list it.

**Geometry (footprint + single base height).** A slant is a **horizontal footprint plus one base height**, with the rise **computed** from step height — there is **no** min/max on the climbing axis (unlike the staircase's min/max block). 2d footprint = `min/max x`; 3d footprint = `min/max x` **and** `min/max y` (a rectangular ground area — the ramp rises along the direction axis and stays flat across the other). The **base height** is the elevation of the ramp's low end (a single value: `base y` on 2d, `base z` on 3d); each tile toward the high end is `step_height` higher, and the top height falls out of the math.

**Direction list (mode-aware, SF's own vocabulary — never compass words).** SimpleFighter uses left/right/forward/backward/up/down, not north/east/etc. (confirmed against `conveyor_belt.nvgt`'s mode-aware direction list — the pattern to copy). Each base direction is shown with **up** or **down** appended, read **literally as an instruction**: *"walk THIS way → go THIS way,"* and the opposite walk always does the opposite.
- **2d:** left up, left down, right up, right down (4 labels).
- **3d:** left up, left down, right up, right down, forward up, forward down, backward up, backward down (8 labels).

A ramp is a **two-way slope**: whichever way climbs, the opposite descends — automatically, so there is no "one-way" ramp and down-ramps need no special option (you walk the downhill way). Because a ramp can be named from either end, some labels are the **same physical slope** (e.g. "left up" ≡ "right down", "forward up" ≡ "backward down"); the duplicate phrasings are kept on purpose so the author picks whichever matches how they picture walking it. (This mirrors that reference game's `east_up`/`west_down` style, in SF words.)

**Step height.** How many whole levels of elevation you gain or lose for **each tile** you move along the slant's direction. **Whole numbers, 1 and up** — **1 is the default** (up one level per tile — the gentlest, a 45° climb); higher = steeper (e.g. 5 = up five levels per tile: x1→5, x2→10, x3→15…). Below 1 isn't possible — a half-level has no floor on SF's whole-level grid — so there's no sub-45° slope. The **form field defaults to `1`.**

**Two surface pickers — each optional, "none" opts out** (so the author chooses per-slant whether the slant builds its own floor or they build it). Each is a full "tile group" modeled on the `build_platform` / `build_staircase` forms — a tile list + tile volume + tile pitch sliders, with the standard preview (space = step, Ctrl+L = land, Ctrl+H = fall). Reuse the shared `builder/construction/platforms/` tiles, so **no new audio is needed**.
- **Bottom surface** — the sloped floor the slant lays under you as you climb, so you don't fall through the ramp itself. "none" → the author builds the ramp floor themselves.
- **Top surface** — the flat landing laid at the high end, so reaching the top of the ramp gives you ground to stand on instead of walking off into thin air. "none" → the author builds the landing themselves.
- **Walls are always the author's job** — if a player could walk off a side/edge and you want to stop them, you build that wall. The slant never makes walls.

**Builder form order.** Follow the standard control order ([[feedback_builder_form_control_order]]): **all input boxes first** — footprint (min/max x, plus min/max y on 3d), then **base height** (form label, renamed from "bottom height" 2026-08; internally `base_height`; defaults to `0` — the low end's elevation, ground level), then **slope amount** (form label; internally `step_height`; defaulting to `1`) — then the **direction** list, then the **bottom surface** and **top surface** groups (each a tile list + volume + pitch sliders), then any checkboxes, then the okay/cancel buttons. Note the step-height input sits with the other inputs *before* the direction list, not after it. Region-input/mode-branch pattern as in `build_staircase`/`build_platform`.

**Runtime mechanic.** When the player moves a tile along the slant's axis while inside the region, adjust `me.y` (2d) / `me.z` (3d) by ±step_height — up in the uphill direction, down the opposite (bidirectional by nature). Key off the player's **actual position change along the ramp's axis, not the key pressed**: 3d/topdown movement is **body-relative** and forward/back go through `body_step()` (there is **no** `step_forward`/`step_backward`), so react to whether `me.x`/`me.y` actually changed. `step_left`/`step_right` (`map.nvgt`) handle the x axis. Play the bottom-surface tile's step sound on each rise/fall.

Unlike the staircase's fill-the-column per-z spawn, the slant's bottom surface is a **diagonal run of tiles** — one floor tile per horizontal step at that step's whole level — so it follows the incline; the top surface is a flat landing at the high end.
- Map line is **space-delimited with mode-dependent length variants** (2d vs 3d), gated in `map_parser.nvgt`; honor the read_/write_ back-compat contract — see [[project_map_format]] and [[project_stability_rules]]. Field order — **2d** (length **12**): `slant minx maxx base direction step_height bottomtile bottomvol bottompitch toptile topvol toppitch`; **3d** (length **14**) inserts the `miny maxy` footprint: `slant minx maxx miny maxy base direction step_height bottomtile bottomvol bottompitch toptile topvol toppitch`. `base` = the low-end elevation (top is computed, not stored); a surface's tile is `none` to opt out. `direction` is an underscored token (`right_up`/`left_down`/`forward_up`/…); comparisons strip underscores, so older no-underscore tokens (`rightup`) still load.

**Resolved (design):** step height is whole-numbers-1-and-up (rise per tile), so the player always lands on **whole levels** — no fractional heights. The bottom surface is a **diagonal run of floor tiles** (one per step) that supports you the whole way up, so there are no unsupported "in-between" heights mid-ramp. Movement reacts to the actual axis position delta (body-relative; `body_step`).

**Still open (implementation detail):**
- Exact map-line field order and the precise `sd.length()` variants per mode.
- **Resolved:** the ramp/landing surfaces are always **plain non-destroyable, non-overlap** floor (dev decision 2026-08) — no destroyable/overlap/health fields on the class or form; spawn the floor tiles as non-destroyable, non-overlap platforms. (Overlap is offered only by platform & staircase; destroyable by platform/staircase/wall/door/sign/clock/calendar/spike/projectile — a slant needs neither.)
- **Slant-aware jump landing (§7) — REVIVED & BUILT (2026-08, was cancelled, then reopened after dev testing).** First cancelled because standing jumps land fine (non-backing floor tiles ARE seen by `user_platform_at`). But the dev later found that a *moving* jump sails clean over a slant without landing on it — in BOTH 2d and 3d. Cause: `user_platform_at` only matches the ramp's single thin surface tile at its exact height, so a jump arc that crosses the footprint above the surface (or strafes across mid-jump in 2d) never coincides with it. Fix mirrors the staircase's `is_staircase_top`/`in_staircase_volume`: added `is_slant_surface(x,y,z)`, `in_slant_volume(x,y,z)` (base_height..per-column surface_height), and `slant_surface_at(x,y)` to `slant.nvgt`, then wired `in_slant_volume` catches into the jump handler (`game_handlers.nvgt`) at the 3d descent, 3d apex, 2d descent, and 2d apex landing points — each SNAPS `me.z`/`me.y` to the column's `surface_height` on land (the ramp has a per-column height, unlike the staircase's flat top). `cur` axis = me.z on 3d, me.y on 2d. **Follow-up fix (dev caught while testing):** landing on a slant while moving DOWN it (e.g. left on a right-rising ramp) played no surface tile sound — the jump-start floor (`me.z<=ty1` / `me.y<=ty1`) fired before `in_slant_volume`, pinning the player one level above the ramp tile at the start height, so `playland`'s `get_all_platform_tiles` found nothing. Fix: `in_slant_volume` is now checked FIRST, and the ty1 floor is suppressed while over a slant footprint (`&& slant_surface_at(me.x,me.y) < 0`), so descent continues to the real per-column surface where `in_slant_volume` lands + snaps + plays the tile sound. Applied to both 3d and 2d descent. Dev tested both 2d and 3d — passes. Changelog entry written (14.3): "Fixed a bug where jumping onto a slant while moving would carry you clean over the ramp...". §7 COMPLETE.

**What it is.** An **invisible rectangular region** that changes how the **ground you stand on** behaves — no platform, no wall, nothing to see or bump. It just quietly overrides properties of the tiles underfoot inside its box. Every knob is optional: set only what you want changed, leave the rest normal.

**Knob set (all optional; final — fall damage settled as "Option A", knob names locked 2026-08):**
- **surface** — which tile the zone targets, picked from a **list** of the platform tiles (same source as the platform/staircase tile pickers, `builder/construction/platforms/*`), with **`any`** at the top as the default. `any` → the overrides apply to **every** tile in the box; pick a specific tile (e.g. `ice`) → only that tile type triggers them (other ground in the box is untouched). **Floor tiles only** — no walls in the list (walls went out with pitch).
- **speed** — walk speed on those tiles (the mud/ice/sand feel). SF's `modspeed` scale (**higher = faster, SF normal 5**) — NOT the reference game's milliseconds. Overrides the player's live speed while on the tile. **No upper cap** (dev decision 2026-08): unlike the player's own A/D keys, which clamp to 1–20, a zone can push speed past 20, since a zone is an authoring tool, not the player's preference. Floor is **1** (the timing math in `game.nvgt` needs `modspeed >= 1`); `-1` is the "leave unchanged" sentinel.
- **jump height** — jump limit/boost in the zone. **`0` = no jumping at all** (a low-ceiling/crawlspace/"no-jump" patch — something the player's own F-keys can't do), `1`+ = a forced jump height, SF normal 5. **No upper cap** (dev decision 2026-08): unlike the player's F-keys, which clamp to 1–20, a zone can force a jump higher than 20. Floor is **0**; `0` is a real value (can't jump) and the separate "leave unchanged" sentinel is `-1`, so they don't collide.
- **fall distance** — how many squares you can fall onto this ground before it hurts, i.e. the **hard-landing threshold** (SF normal **8**: a drop of fewer than 8 is a free soft landing, 8+ is a damaging hard landing). Lower = short drops sting; higher = long safe falls (near-fall-zone, but tunable).
- **fall damage** — the **multiplier** for how hard each fallen square hits once a fall crosses the threshold (overrides `fallmod`, SF normal **21**; it's a multiplier × distance, not a flat amount). Higher = brutal ground; lower = gentle.

Fall damage was settled as **Option A**: SF has no flat "normal-landing damage" (short landings are free) — just one multiplier (`fallmod`) plus the hard-fall threshold — so the reference game's `land_damage`/`hardland_damage` split was replaced by these two SF-native knobs (**fall distance** = the threshold, **fall damage** = the multiplier).

**Form defaults & baselines (dev-settled 2026-08).** Every knob's form field defaults to **"leave unchanged"** (the `-1` sentinel for the numeric knobs, `any` for surface) — **NOT** to the normal value. A zone touches only the knobs the author actually sets; this is what protects the player's own live speed/jump settings (an unset knob leaves them alone) and what makes layering work (an unset knob falls through to an outer zone). The **normal baselines** — speed **5**, jump height **5**, fall distance **8**, fall damage **21** — are simply what "leave unchanged" gives you, and must be **written into the help topic** so authors know what they're deviating from. A tile zone with **every knob left unchanged does nothing** — a harmless no-op that just defines an empty region (matches the reference game). (Contrast the slant's `step height`, which is a *required* field with a real default of `1`.)

**Dropped on purpose (dev decision):** **volume and pitch**. The platform/staircase build forms already give the author per-tile volume + pitch sliders, so a zone override would duplicate an author tool that already exists. And since **pitch was that game's only wall-affecting knob**, dropping it means the tile zone **never touches walls at all** — it's purely about the ground you stand on. That's the guiding rule we used: **keep a knob only if there's no author-side, area-specific control for it already** — volume/pitch have one (the build form) → dropped; speed/jump height do NOT (only the player's global A/D/F and F1–F3 keys exist, which are the player's own preference, not an authoring tool) → kept.

**Three behaviors (all kept from the reference game):**
1. **Surface filtering** — blank surface = every tile in the box; a named tile = only that tile type triggers the overrides.
2. **Layering** — when zones overlap, the **later-defined** zone wins on any knob they both set; a knob the inner zone doesn't set still uses the outer zone's value. Lets you carve exceptions (a big slow-swamp zone with an even-slower pocket inside).
3. **Auto-reset on exit** — step off the zone's tiles and every override lifts on its own (no "reset zone" needed). The restore is a **proper reset to the value the player had AT ENTRY** (dev-confirmed 2026-08): the loop saves the player's own value the moment an override becomes active, drives it while inside, and restores that saved entry value on exit. If the player changes their own speed (A/D) or jump height (F-keys) *while inside* the zone, that change is **discarded** on exit, not kept — deliberately, since the zone values are uncapped and must never leak into the player's own preference. Save/restore is **per-knob**: a knob the zone leaves unchanged (`-1`) is never saved or touched, so the player's A/D/F for that property keep working normally inside the zone.

**Key integration points (from a read-only code survey — the whole feature is a save-override-on-enter / restore-on-exit layer over three plain globals):**

## Flux zone — a per-step stat accumulator element (DESIGN SETTLED 2026-08, not yet built)

A NEW standalone builder element — NOT baked into the tile zone. The dev chose a separate element to avoid mixing two philosophies in one form: the tile zone SETS values that revert on step-off, whereas a flux zone PERMANENTLY accumulates. Distilled from an external reference game's "triggers" — the one non-duplicative idea from that comparison (SF's sensors/switches/heal zones/spikes/trampolines already cover the rest). A flux zone is a ranged region that **nudges the player's own stat a little with EACH STEP** taken on a matching tile inside it, and the change **sticks** after you leave (the whole point: "faster the more I walk"). Name "flux zone" chosen by the dev over ramp/trigger/drift (ramp collides with slants, trigger with sensors, drift faintly implies being carried).

- **Knobs: surface + four INDEPENDENT per-step stats — speed, health, stamina, shield.** NO jump (odd use), NO fall (landing-time). Shield is its OWN knob (dev added 2026-08), so health/stamina NEVER redirect to shield the way heal zones do — all four are separate. Every knob applies in EVERY mode incl. topdown (none are altitude-based).
- **Each stat knob = a signed per-step amount:** whole number, magnitude ≥1, no max; positive ramps up, negative drains, **0 = off (default)**. Applied once per real step.
- **Value bounds:** no artificial floor EXCEPT speed, floored at 1 (technical: `modspeed<1` freezes the walktime recompute). Health→0 = death, stamina→0 = empty, shield→0 = breaks via the existing `shieldstrength<=0` logic in `game.nvgt`. The **shield step only acts while a shield is raised** (`shieldon==1`), mirroring heal zones' shield handling — no-op with no shield up. (The dev's "min 1" = the per-step AMOUNT magnitude, NOT a value floor.)
- **Targets the player's OWN values:** speed → `player_own_speed += delta` (live `modspeed` derives from it, per §4b); health → `health += delta` (0..maxhealth); stamina → `stamina += delta` (0..maxstamina); shield → `shieldstrength += delta` (0..maxshieldstrength, only if `shieldon`). Persists on step-off.
- **No sound** — silent like the tile zone (the ground's own step sounds play). Dev confirmed only heal zones needed audio.
- **Reset:** death resets speed via `reset_move_stats()` (built 2026-08, `checkpoint.nvgt`) and health/stamina/shield via `charparse()` + the shield reset; stamina auto-regens (health does NOT — needs the heal key).
- **Runtime hook:** `playstep()` (`map.nvgt`) is the single per-step choke point — every real step (`step_left/right/up/down`, `body_step`) calls it and it already runs per-step zone work (heal/safe). Add `fluxzone_step()` there: scan covering, surface-matching flux zones (layering, later-index-wins), apply the four deltas.
- **On-disk format (clean — brand-new element, no back-compat dance):** `flux_zone minx maxx miny maxy [minz maxz] surface speed_step health_step stamina_step shield_step` → length **10** (2d/topdown) / **12** (3d).
- **Scaffolding:** mirror a zone entity (`heal_zone`) — class + `@[]` array + spawn/read/write/build/destroy_all + menu entry (alphabetical in zones: "flux zone" sorts between "fall zone" and "heal zone") + parser dispatch + `clearmap`. Zone arrays compacted (no null-guard).
- **Proposed build sections:** (1) data+lifecycle+read/write, (2) form (surface list + 4 step input boxes, default 0), (3) runtime `fluxzone_step` in `playstep`, (4) wiring (menu/parser/clearmap), (5) docs (new `flux_zones.txt` + changelog).
- **Build status (2026-08):** §1 DONE (`src/includes/builder/zones/flux_zone.nvgt`): class `fluxzone` + `fluxzones` array + `player_in_fluxzone` (box geometry) + `spawn_fluxzone` + `destroy_all_fluxzones` + `read_flux_zone`/`write_flux_zone` (len 10 2d/topdown, 12 3d). Compacted array, no sound, four `double` step fields. Inert until wired. §2 form DONE (`build_flux_zone`: coord inputs + 4 step input boxes default "0" + surface list with "any"; all steps shown in every mode; minus allowed so drains are typeable; empty step → 0; no audition/no range validation). §3 runtime DONE (`fluxzone_step()` in `flux_zone.nvgt`, hooked into `playstep()` beside update_healzone/safezone): per real step, surface filter via `gmt` + later-built-wins-per-knob layering (0 = knob not set, doesn't override outer), applies to `player_own_speed` (floor 1 here), `health`, `stamina`, `shieldstrength` (only if `shieldon==1`); health/stamina/shield bounds + death + shield-break left to the game loop's existing clamps. Speed change lands next frame (modspeed re-derives). §4 wiring DONE (menu display/id/`converted_3d`/dispatch in `map_menu.nvgt` — "flux zone" between fall & heal, NOT in `excluded_topdown` since it works in all modes; `read_flux_zone` dispatch in `map_parser.nvgt` len 10/12; `destroy_all_fluxzones()` in `clearmap`). Feature is now live end-to-end. §5 docs DONE — `sf/docks/builder/flux_zones.txt` (includes a three-way "differs from heal zones and tile zones" comparison, each on its own line, dev-requested) + 14.3 changelog entry "You can now build flux zones...". **WHOLE FLUX ZONE FEATURE COMPLETE** — drop this section from the backlog once 14.3 ships.

### Builder templates — reusable hand-authored map-object packs, placed by reference (DESIGN SETTLED 2026-08; scaffolding started)

**OFFICIAL NAME: "builder templates"** (dev-confirmed 2026-08 — use this term consistently).

A possible **14.4** feature. Inspired by an external reference game's "template builder" (prebuilt compound objects — box, table, chair, bed, couch — placed as one unit instead of hand-building each wall/platform). The dev doesn't know that game's internals beyond it having flags/ids (both irrelevant to SF).

**THE DEV'S CHOSEN APPROACH (this is the design, not a fork to resolve): templates are hand-authored map-line snippets on disk, NOT procedurally generated.** The dev is strong at 2d building and weaker at 3d, and explicitly does NOT want the game guessing/auto-generating template geometry (a machine-guessed 3d couch would be unusable to them). Instead **a human authors each template by hand** as a partial map in the exact on-disk map format, in whatever mode they're comfortable with, and the engine's ONLY job is to **read that file and stamp its lines into the current map at an author-chosen anchor**. No geometry generation anywhere — the creativity is all in the hand-authored file.

**RESOLVED — how the reference game actually worked (dev deduced 2026-08, matches its changelog): its templates were HARDCODED GENERATORS, not stored files.** Each template was a bespoke code function with its own form; the form fields were that generator's INPUTS — dimensions (Table's min/max x/y, Chair's height, the stairs' width/step count = how big to compute) plus tile/wall pickers (Frame Type / Surface Type / Seat Type = what material to build from). Pressing okay ran the code, which *computed* the map lines from those choices and wrote them in ("whatever you chose translated to the map's lines"). There was no template FILE — the "template" WAS the function. It never took a plain x/y/z and stamped a pre-made object. This is the clean fundamental fork, now fully resolved: **reference game = template-is-CODE (a generator) → per-template form, resizable/fit-to-box, but every template is a coding effort with generation-bug risk (their real "wrong axis in 2D" bug); SimpleFighter = template-is-DATA (a `main.sif` file) → one generic anchor form, fixed size, but zero per-template code, no generation bugs, and anyone can author one by dropping a folder.** This explains every downstream difference (per-template vs one generic form; resizable vs fixed) and is why the data approach fits SF better (no code per template, screen-reader-friendly hand-authoring, plays to the dev's 2d strength). Nothing left to reverse-engineer from the reference game — SF's approach is deliberately the opposite.

**On-disk layout the dev established (2026-08, reorganized — a template IS a mini-map):** `sf/data/builder/templates/<name>/` holding **`main.sif` + `meta.sif`** — the SAME pair a real decompiled map uses (`main.sif` = content/geometry, `meta.sif` = metadata). **Dev's stated intent (2026-08): a template should "look like a real map, but watered down"** — deliberately mirror a real map's on-disk shape (uniquely-named folder, main+meta, mode declared in meta) so the format stays familiar and the loader can reuse map-shaped logic, just simpler (geometry-only, fewer meta fields). Folders are **flat** (no `2d/`/`3d/`/`topdown/` mode dirs — an earlier draft had those; the dev flattened them). `main.sif` is a block of **real SF map lines** in the on-disk format (a partial map). `meta.sif` is three `key=value` lines (same forgiving key=value parsing as a map's meta — value = whole line after `=`, quotes optional; see the description-quoting note the dev confirmed 2026-08):
  - `mode=2d` — which map mode the template targets. **This field is the mode gate** (not the folder anymore): the loader reads each template's meta and offers only those whose `mode` matches the current map.
  - `category=none` — a grouping slot for the builder menu; `none` placeholder for now.
  - `description=A comfortable looking couch.` — friendly one-liner (hand-written unquoted, reads back fine).
  **Consequence of flattening — one flat name namespace across all modes:** you can't have both a `2d/couch` and a `3d/couch` anymore (both want `templates/couch/`); a same-object-different-mode template needs a **distinct folder name** (e.g. `couch3d`) with its mode set inside its own meta. New folder = new template, no code wiring (auto-discovered like help topics / effect presets). Current roster (all `mode=2d`): advanced_chair, basic_chair, bed, couch, table, tub.

**GEOMETRY-ONLY — strict vocabulary (dev-decided 2026-08).** A template contains **only static geometry: plain (fixed) platforms, staircases, and walls.** NOTHING else — no moving/vanishing platforms, and **no zones of any kind** (text_zone, tile_zone, …). This mirrors the reference game, which "strictly cared about platforms, staircases, and walls only" when stamping a template and left everything else for the author to build afterward. So a template names nothing and adds no behavior — if the author wants the object to announce itself they add a `text_zone` by hand after placing, and if they want a walk-through feel they add a `tile_zone` by hand. Earlier drafts had baked-in `text_zone`/`tile_zone` lines (and this note once praised them); those were **removed from all 2d examples 2026-08** per this decision — the drafts are now pure wall/platform/staircase lines. Example (`couch/main.sif`): six `wall`/`platform` lines forming the couch, nothing else. Two authoring styles both live within this vocabulary: *composed* (advanced_chair — many walls/platforms of generic tiles shaped into the object) and *themed single entity* (basic_chair — one `staircase` painted with a dedicated `chair` tile pack; leaner, but depends on that pack existing).

**Why it fits SF perfectly.** The map format is a flat list of positional lines in `main.sif`, so "stamp a template" = read N lines, offset them to the anchor, append, spawn. And SF has **no object IDs or flags** (effect space is the lone ID-taker, effectively internal) — so the stamped lines are plain and independent, nothing to keep unique or rewire. The reference game's per-template "flag" convenience has **no SF equivalent and is dropped**; since templates are geometry-only, naming isn't a template concern at all — the author adds a `text_zone` by hand afterward if they want one.

**Precedent to mirror for the plumbing — effect-space presets + help-topic auto-discovery.** `effect_space.nvgt` already does "named, reusable, saved-to-`.sif`, works-on-any-map" via `list/load/save/rename/delete` over a per-type folder; the builder-template loader is the same read-a-`.sif`-folder shape (list the `templates/*/` folders, read each `meta.sif`, offer those whose `mode` matches the current map, then read the chosen template's `main.sif`). Auto-appearance mirrors the `docks/builder/*.txt` help scan. (Unrelated to SF **macros** in `macfuncts.nvgt` — combat hotkeys, not builder.)

**The ONE core engine problem — anchoring / coordinate offset.** The authored lines carry near-origin absolute coords (the drafts start around x=5). To place a template somewhere else, the engine must add the anchor offset to every coordinate token — but coordinates sit at **different token positions per entity keyword** (a `wall`, a `platform`, and a `staircase` line each put x/y/z in different slots), and 2d vs topdown vs 3d shift those positions again. So the offsetter needs a per-keyword, per-mode map of which tokens are x / y / z — and, given the geometry-only vocabulary, it only has to handle those three keywords (plain platform, staircase, wall), not every entity type. This is the real work of the feature; everything else (list, read, append, spawn, help topic) is light.

**Placement mechanic — LEANING to camera-marker anchor (from the reference game's method, inferred from its changelog/readme 2026-08).** The reference game never stamped a file — it **generated** template geometry from a per-template form (tables/boxes/chairs/stairs/shelves/beds/arches/pits "from a single form"), which is exactly the procedural approach the dev rejects (and it caused a real "built on the wrong axis in 2D" bug there, the class of failure hand-authoring avoids). BUT its **positioning** method transfers: templates were placed/sized by **camera markers** — "mark the two corners… the template arrives filled in… lands exactly inside what you marked." SF already has that camera-marker system (`G+J/K/L…` min/max x/y/z) and already prefills build-form coords from it (e.g. effect space). So the natural anchor for SF's fixed snippets is a **camera marker**: mark where you want it, engine re-bases the authored coords to that marker (the "re-base to anchor" option — clearly better than "append at authored coords + hand-edit", which would defeat reuse). Difference from the reference game: they marked TWO corners and *scaled* the generated geometry to the box; SF's snippets are **fixed authored size**, so anchor to the **single minimum-corner marker** and keep the authored dimensions (no stretch-to-fit). Pending dev sign-off, but this is the recommended mechanic.

**REPOSITION vs RESIZE — key clarification (dev raised 2026-08).** The dev authored the drafts using absolute coords based on where they stood on the map and worried the templates are "locked" there / wished they could "resize so they go anywhere." Untangle two different things:
- **Reposition (place anywhere) = fully solved, no re-authoring needed.** The loader normalizes each template to its OWN minimum corner (subtract the min x/y/z across all its lines) so the authored absolute position is irrelevant — a couch authored at x=5 or x=500 both become "10-wide shape," then offset to the drop anchor. **The existing 2d drafts are fine as-is**; their absolute coords get normalized away. This is exactly the "go anywhere" freedom the dev wants and it comes for free with the anchor-offset.
- **Resize (stretch geometry to a bigger/smaller footprint) = genuinely hard, and deliberately OUT of scope.** Hand-authored snippets don't encode which parts stretch vs stay fixed (a couch's arms should stay 1 tile while only the seat lengthens — the file can't say that), so a naive stretch corrupts the shape. This is precisely WHY the reference game *generated* its geometry from a form (generation is what let it scale to a marked box). SF's chosen hand-authored approach trades resizability for authoring control + zero geometry-guessing. Want a bigger couch → author a second `couch_large` template (cheap — just another text file), don't stretch the small one. Recommendation: ship "place anywhere at fixed size"; do NOT attempt true resize.
- **"What if the placement form asked for min/max x/y/z (a two-corner box) instead of a single anchor — would that add resize?" (dev asked 2026-08).** No, not cleanly. A box only gives the engine the *input* a resize needs; to USE the max corner it must pick a scaling rule, and the only general one is "multiply every coord by (box size ÷ template size)." That uniform stretch has two failure modes: (1) it **warps structured objects** — scaling is uniform but a couch's arms should stay 1 tile while only the seat lengthens, a staircase's step ratio should hold; uniform stretch fattens arms and distorts steps (this is exactly why the reference game *generated* geometry — a generator recomputes "N steps to fill this height," a fixed file can't); and (2) it yields **fractional tile positions** (a leg at x=5 stretched 2.5× → x=12.5), which sound wrong and need rounding that distorts small objects further. Fit-to-box IS clean for **rectangle/region-shaped templates** (a plain floor, a wall-box, an empty room — no internal structure to warp; a single platform x5..15 → x5..40 is just a wider floor), and mangles **structured furniture**. So min/max-on-every-template would resize rectangles and corrupt chairs. The honest way to offer resize is a SEPARATE, explicitly-resizable **region template type** (flagged in its `meta.sif`, e.g. `resizable=true` or `category=region`), kept distinct from the fixed furniture library — a real, separable follow-on feature, added complexity. Default stays single-anchor fixed-size.
- **"What if I zero the coords and let the min/max form supply them?" (dev asked 2026-08) — works, but ONLY for a SINGLE-element template.** If a template's ONE line is zeroed (e.g. `staircase 0 0 0 0 1 chair 0 100 false false`), the form's min/max x/y have an obvious home — they drop straight into that lone entity's four coordinate slots (`→ staircase 10 10 5 12 1 chair …`), giving a genuinely **resizable single-entity template**; the `0 0 0 0` is just a placeholder the form fills. This is the SAME clean case as the "region template" above (a lone rectangle whose box you supply — fit-to-box is well-defined for one entity). It does **NOT** generalize to multi-element templates (couch=6 lines, advanced_chair=7): one box can't map onto several relatively-arranged pieces — stuff the same min/max into all of them and they collapse onto one rectangle; spread it proportionally and you're back to warp + fractional tiles. So the mechanic is: **single entity → min/max form works; multiple entities → single-anchor fixed size only.** To use it, the template must DECLARE it (meta flag like `resizable=true`/`category=region`) so the builder shows the min/max form vs a single anchor — don't infer it from "are the coords all 0." Honest caveat: a resizable single-staircase template is *almost* just the normal staircase builder — the template only pre-bakes the tile (`chair`) + fixed health/volume/pitch/destroyable/overlap, so for one-entity objects it's a "pre-flavored entity preset," not a big win; templates earn their keep on the MULTI-element (fixed-size) objects.

**The form — ONE generic form for ALL templates, "fully baked" (dev-decided 2026-08).** The reference game had a **bespoke parametric form per template** (its Table form: min/max x, min/max y, frame type + browse, surface type + browse; its Chair form: x, y, height, seat type + browse) — but ONLY because it **generates** geometry, so every field is a generator input (the min/max box is the fit-to-box the generator fills; frame/surface/height are what it builds from). SF's hand-authored snippets **bake all of that into the template's `main.sif`** (dimensions, every tile, height are already written in the file), so an SF template form has **nothing those forms ask**: no frame/surface/height fields, no min/max box (fixed size, not fit-to-box), no per-template variance. Result: **one generic placement form for every template** (SEE the "UI — SETTLED" section below for the final shape — an **NPC-build-style form**: coordinate inputs (marker-prefilled) + `path`/`category`/`subtype` lists, NOT a bespoke per-template form). The point that survives: the form asks **nothing about the geometry** — no tile/size/frame/height fields — because all of that is baked into the file. **"Fully baked" chosen over swappable knobs** (dev 2026-08): the tile a template uses is whatever its file says; want a marble table → author a `table_marble` variant (cheap — another text file), rather than exposing a surface picker that would need per-template knob declarations + tile-token substitution in the loader. This keeps the hand-authored, no-guessing, zero-generation philosophy intact.

**SF form idiom (NOT the reference game's) — must follow when built:** SF uses the **audio form** with inline **lists** you arrow through (tile preview on space / Ctrl+L / Ctrl+H), sliders, input boxes, in the fixed order inputs → lists/sliders → checkboxes → okay/cancel ([[feedback_builder_form_control_order]]) — **NOT** the reference game's "Browse …" buttons that open a separate picker. So template choice is an inline list; escape/cancel speaks "canceled".

  **ADD/authoring — RESOLVED 2026-08 (Q3): a multiline box, paste-anything, validate-on-save (in-game "rawmap").** The add form is a **multiline text input** (`create_input_box(..., multiline:true, multiline_enter:true)`) where you type/paste the template's geometry lines in-game — the "rawmap in an external editor, but done inside the game" workflow. Plus three identity fields: **name** (subtype), **category**, and **description**. **RESOLVED 2026-08 how these behave (dev, after reviewing the npc/shield/weapon add forms):**
    - **category = a LIST populated dynamically from the existing category folders** (`find_directories` on `templates/*`), i.e. the *weapon-manager* style (weapon reads categories from folders; NPC hardcodes them — templates follow weapon). **New categories are created BY HAND** (make the folder, e.g. the dev created `bedroom/`), NOT through the form — the form only lists what exists. This matches the managers, none of which create categories in-form.
    - **name = a typed TEXT input** — the one NECESSARY divergence from the other managers. They pick subtype from a list of pre-existing folders because those entities have sound assets on disk; a template has NO audio, so nothing pre-exists to pick, and the author types a brand-new name.
    - **description = a text input** (→ `meta.sif`). On save it writes `templates/<category>/<name>/main.sif` = an **auto-prepended `mode <current-map-mode>` header** + the box's lines, and `meta.sif` = `description=…` (mode comes from the map being edited, so the author never types it). NOT the camera-marker/save-selection style (set aside).
  **VALIDATION — RESOLVED 2026-08 (revised): PASTE ANYTHING, VALIDATE + NOTIFY ON SAVE (NOT silent strip, NOT auto-trim-on-paste).** Modeled on the **`rawdata`/`rd` command** (`command_parser.nvgt:1212`), which reads the clipboard, runs **`validate_map_data(lines)`** (`mapfuncts.nvgt:97`), and if invalid **notifies ("The clipboard data is invalid") and refuses to write**. Corrected template flow:
    - **Paste is unrestricted** — the box accepts anything (a whole rawmap dump, fragments, junk); NO filtering on paste. The author manually trims to the geometry they want (the "rawmap-in-game, remove the parts you don't need" workflow). *(This SUPERSEDES the earlier "auto-trim/geometry-only filter on paste" AND the "silent strip on save" ideas — nothing is silently removed.)*
    - **On save (commit button), a TEMPLATE-SPECIFIC validator scans the box** and requires every non-empty line to be a valid geometry line: first token `platform`/`staircase`/`wall` **and** well-formed (correct field count for the map mode). Anything else — a stray `mode` line, `minx/…` bounds, `mplatform`/`vanishing_platform`, a zone, an npc, or malformed junk — is INVALID.
    - **Invalid → notify the author** (rawdata-style; ideally name the count/offending line) **and refuse to save** until fixed. **Clean → write** `main.sif` (auto-prepended `mode` header + the lines). So a `mode` line left in the box is flagged invalid (the form supplies the real header) — directly addressing the dev's worry about a stray `mode` corrupting mapmode (which is creation-locked, [[project_stability_rules]]).
    - **Cannot reuse `validate_map_data` directly** — it *requires* the map bounds header (`minx/maxx/miny/maxy`) a template deliberately lacks; build a template validator on the same scan-lines-and-gate pattern (whitelist geometry keywords + field-count check).
    - Expansion-time defense still applies: the offsetter only handles the three geometry keywords and reads-but-never-spawns the `mode` header, and silently skips any line it can't parse — so even a bad line that slipped through is inert.
    - Clipboard API available (`clipboard_read_text`/`clipboard_copy_text`, `bgt_compat.nvgt`; `menu_zone.nvgt` has a paste-from-clipboard precedent). Pasted absolute coords need no author-time normalization — the placement offsetter re-bases to the template's own corner. (EDIT/VIEW buttons reuse the same multiline box: edit = editable + same save validation, view = `read_only:true`.)

  **EXPANSION MODEL — RESOLVED 2026-08: REFERENCE (not stamp).** Placing a template writes **ONE reference line** — NOT N stamped geometry lines. The reference **expands at load** (look up the template, offset its `main.sif` geometry to the placed anchor, spawn the pieces) and **bakes into raw lines when the map compiles to a `.map` pack**, so shared packs stay self-contained even though the decompiled source is compact. Why chosen: keeps `main.sif` one-line-per-object (easy move/delete = edit/remove one line; no "undo last placement" crutch needed) and short for screen-reader scanning; the decompiled-source→template coupling is paid off by the compile-time bake + the global-and-map storage. Consequences now firm: post-placement move/delete is a one-line edit. **Dangling reference (template missing at load/compile) — RESOLVED 2026-08: SKIP SILENTLY** (the object just doesn't appear; no warning). Dev's reasoning: players notice a missing object when they navigate the map, and it's consistent with SF's existing silent-missing-content handling. (Trade accepted: a template missing at compile time silently drops from the shared pack — no compile-time warning.)
  **LINE FORMAT — RESOLVED 2026-08 (Q3). Generic `tpl` keyword** (NOT the earlier `tpl_<name>` prefix — that idea is SUPERSEDED): **`tpl <x> <y> <path> <category> <subtype>`**, or with z on 3d: **`tpl <x> <y> <z> <path> <category> <subtype>`**. Full 2d example: **`tpl 5 2 any bedroom couch`** (x=5, y=2, path=`any`, category=`bedroom`, subtype=`couch`). Order: coords first, then path, then category, then subtype (the template name). Path values `global`/`map`/`any` (resolve map-first-then-global as before). `tpl` is one fixed keyword (collision-free vs the 79 map keywords), the name is the `subtype` field — so template names can be anything without colliding. **`category` IS needed in the line and IS a folder** (resolved — see storage note): the loader locates the template at `templates/<category>/<subtype>/`, so both tokens are load-bearing.

**Post-placement editing — known friction + the cheap mitigation (dev raised 2026-08).** Once a template is stamped it becomes N ordinary, ungrouped map lines; moving or deleting it later means editing those lines individually via the builder line editor. Honest framing: the template does NOT *add* editing cost — those are the same N lines any hand-built object of that shape would have, so the template is pure win on the hard part (laying N correct lines in one action) and neutral on editing. Resizing-after-placement is likewise just normal map editing (and resize was scoped out of templates anyway). The real friction is *moving* a placed unit; the realistic answer is **delete-and-re-place, not nudge**. The cheap, high-value affordance to build for that: **"undo / remove the template I just placed"** — have the builder remember the range of lines it just wrote so a mis-placement becomes undo → re-anchor → re-stamp instead of hand-deleting N lines (the common case is "oops, wrong spot, redo now," not "move one placed a week ago"). **Steer AWAY from** true "select a placed template and drag it as a group later" — that needs a shared group tag/ID on the stamped lines, which collides with SF's no-object-IDs rule ([[project_stability_rules]]); doable but against the grain, likely not worth it. Recommendation: ship placement + "undo last placement"; accept long-after move = delete+replace; don't build grouping.

**RECONSIDERED — "save your own selection as a template" (dev reopened 2026-08).** The dev hand-authored the starter library, but wants the effect-preset-style *save-current-state* path too: turn something already built in a map (their example: a well-crafted fountain buried mid-map) into a reusable template WITHOUT the raw-map-export-then-hand-delete-tens-of-lines misery. This is the geometry analog of `save_effect_preset` — *capture current state → name it → write a reusable `.sif`* — the exact parallel the dev drew at the very start of this brainstorm. **Clean mechanism = region capture via camera markers:** (1) author marks the object's bounding box with SF's existing min/max x/y/z camera markers (`G+J/K/L…`); (2) picks "save selection as template"; (3) the tool **scans the map's `main.sif`**, grabs geometry lines whose footprint is inside the box, **normalizes them to the box's minimum corner** (subtract it → position-independent; the SAME per-keyword coordinate-token offsetter placement needs, run in reverse), and **writes a new `templates/<name>/`** folder — `main.sif` (captured lines) + `meta.sif` (`mode` auto-set to the current map's mode, name/description typed). Seconds instead of hand-extraction. **Reuses existing machinery** (less new code than it looks): camera markers (selection), the map-line parser (scan), the placement offsetter (normalize — shared), the effect-preset save flow (name + write `.sif`). **Three decisions to settle:** (a) **containment = fully-inside only** (safer than "overlaps"; won't grab half a wall running out of the box — author marks a bit generously); (b) **filter to the geometry-only vocabulary** — capture only plain platforms, staircases, walls; skip everything else in the box (zones, NPCs, moving/vanishing platforms) so saved templates are identical in kind to hand-authored ones and placeable by the same 3-keyword offsetter; (c) **partial pieces poking out of the box are skipped** (per fully-inside), so mark around the whole object. **Scoping:** an accelerator LAYERED ON TOP of the base placement feature, not a prerequisite — the hand-authored library works without it — but it's what makes templates worth using for objects discovered AFTER building, not just planned up front. Natural v2 after base placement ships.
